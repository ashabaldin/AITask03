# Универсальный HTTP-сервис объектов 1С

Статус: утверждена пользователем. Источник требований — ТЗ универсального сервиса и решения
текущей сессии. Выбран один общий разбор для справочников и документов: имя типа
выбирает метаданные, правила значений и записи общие, список записываемых
стандартных реквизитов зависит от вида.

Эта спецификация заменяет контракт счетов из
[2026-10-25-shop-invoices-design.md](2026-10-25-shop-invoices-design.md).
Счёт на оплату покупателю создаётся тем же `POST /object`. Прежний документ
остаётся историей реализованного контракта; план, который на него ссылается,
не переписывается.

## Назначение и границы

Разработчик внешней системы и его ИИ-ассистент без доступа к конфигуратору
находят тип объекта, читают его поля и собирают тело запроса. Сервис описывает,
ищет, читает и создаёт справочники и документы. Магазин заводит партнёра,
склад оформляет поступление, внешняя бухгалтерия читает реализацию. Счёт на
оплату — частный случай документа.

Успешное создание возвращает идентификатор нового объекта. Повтор того же
запроса создаёт второй объект: защиты от дублей нет. После потери ответа повтор
нельзя считать безопасным. Ошибка заполнения не оставляет записанного объекта.

Проведение, изменение и удаление не входят в задачу. Регистры, константы,
отчёты, обработки, планы обмена, задачи, бизнес-процессы и прочие виды
метаданных не поддерживаются: сервис отвечает понятным отказом. Сервис не
считает цены, скидки, НДС и суммы и не вызывает заполнение нового объекта.
Дополнительные сведения БСП не читаются и не записываются: это регистр, отдельной
операции для него нет.

Основная конфигурация не меняется. Доработка остаётся в расширении
`СчетаМагазина`. Имя HTTP-сервиса, его UUID, RootURL `objects`, имена
обработчиков и режим сеанса `AutoUse` / `sessionMaxAge` 20 уже заведены и
сохраняются.

## Рассмотренные подходы

1. Один общий разбор. Описание, преобразование значений, поиск, проверка
   заполнения и формат ошибки общие для справочника и документа. Стандартные
   реквизиты записи различаются. Выбран пользователем: счёт не расходится с
   остальными типами, а текущие общие модули обобщаются без второго контура.
2. Отдельные ветки справочника и документа за теми же маршрутами. Особые
   правила вида проще изолировать, но общую логику пришлось бы вести дважды.
3. Прежние пути счетов рядом с универсальными. Два контракта. ТЗ заменяет
   сервис счетов, в расширении уже есть только маршруты `objects`.

## Размещение и HTTP-контракт

Исходники расширения — каталог `src/` этого EDT-проекта. Пути ниже указаны
относительно корня сервиса `objects`.

| Метод и путь | Назначение | Успешный статус |
| --- | --- | --- |
| `GET /types?q=…&limit=…` | Найти типы по части имени или синонима | `200` |
| `GET /type?name=…` | Описание типа | `200` |
| `GET /search?type=…&q=…&limit=…` | Найти объекты типа | `200` |
| `GET /object?type=…&id=…` | Прочитать объект | `200` |
| `POST /object` | Создать справочник или непроведённый документ | `201` |

Имя типа — как в метаданных: `Справочник._ДемоПартнеры`,
`Документ._ДемоСчетНаОплатуПокупателю`. Других операций сервис не предоставляет.
Доступ — обычная аутентификация HTTP-сервиса учётной записью 1С, с её правами.
Привилегированный режим не включается.

Тела запросов и ответов — JSON в UTF-8. У ответов
`Content-Type: application/json; charset=utf-8`, без BOM. Для создания клиент
передаёт `Content-Type: application/json`, допустим параметр `charset=utf-8`.

Внешние ключи JSON английские: `type`, `header`, `tables`, `id`, `error`,
`items`, `hasMore`, `name`, `title`, `kind`, `fields`, `rules`, `isFolder`.
Имена реквизитов 1С внутри `header` и строк таблиц — русские технические имена.

Пример формы создания, а не перечень полей:

```json
{
  "type": "Справочник._ДемоПартнеры",
  "header": {"Наименование": "Новый партнёр", "ЭтоГруппа": false},
  "tables": {}
}
```

`type`, `header` и `tables` обязательны. `tables` — объект, даже если табличных
частей нет. Необязательные значения можно не передавать: они остаются штатными
пустыми значениями нового объекта. Неизвестные ключи и поля с `writable=false`
отклоняются.

Успешные чтение и создание возвращают одно и то же тело. Создание отличается
статусом `201`.

```json
{
  "type": "Документ._ДемоСчетНаОплатуПокупателю",
  "id": "00000000-0000-0000-0000-000000000000",
  "header": {},
  "tables": {"Товары": []}
}
```

`id` повторяет ссылку объекта. `header` содержит все реквизиты шапки, включая
стандартные. `tables` содержит все табличные части; порядок элементов массива —
порядок строк. Номер, дата, код, признаки и ссылки читаются из сохранённого
объекта, а не из предыдущего запроса.

## Поиск типов

`q` — непустая после удаления внешних пробелов подстрока. Регистр не учитывается.
Совпадение ищется в техническом имени и в синониме. Символы шаблона — обычные
символы. `limit` — целое от 1 до 100, по умолчанию 20. Неверные параметры
отклоняются.

В список входят только справочники и документы метаданных конфигурации с
расширениями. Сортировка — по имени типа. Ответ получает не более `limit + 1`
типов и возвращает не больше `limit`.

```json
{
  "items": [
    {"name": "Справочник._ДемоПартнеры", "title": "Демо: Партнеры", "kind": "catalog"}
  ],
  "hasMore": false
}
```

`kind` — `catalog` или `document`. `title` — синоним. `hasMore=true` означает,
что строку поиска надо уточнить или увеличить лимит. Постраничной выдачи нет.
Описание типа не проверяет права на данные: имена метаданных доступны учётной
записи сервиса. Права проверяются на поиске, чтении и записи данных.

## Описание по метаданным

Схема формируется при запросе по метаданным действующей конфигурации с
расширениями. Новый реквизит или табличная часть появляется в ней автоматически.
Состав полей в этой спецификации не фиксируется.

Ответ содержит `type`, `title`, `kind`, `fields`, `tables`, `rules`. Для
справочника дополнительно `hierarchical` и `owners`.

`hierarchical`:

| Значение | Когда |
| --- | --- |
| `none` | Справочник не иерархический |
| `folders` | Иерархия групп и элементов |
| `items` | Иерархия элементов |

`owners` — массив имён типов владельцев, например `["Справочник._ДемоПартнеры"]`.
У справочника без владельцев массив пустой. У документа этих двух свойств нет.

Для реквизита возвращаются:

- `name`, `title`, `writable`, `required`, `types`;
- `reason` — если поле недоступно для записи.

Для табличной части возвращаются `name`, `title`, `writable`, `required`,
`fields` и при необходимости `reason`. `required` у поля берётся из проверки
заполнения метаданных. У табличной части — из её настройки. Обязательность поля
строки сама по себе не означает обязательность хотя бы одной строки.

`rules` поясняет окончательное решение штатной проверки заполнения, формат дат,
смысл `null`, запрет расчёта сумм и формат хранилища значения. Схема не обещает
вывести условные правила из произвольного кода обработчиков.

Элемент `types` содержит `name` и `kind`. Имя типа значения — дискриминатор
составного значения. Оно же указано в схеме.

| `kind` | `name` | Дополнительно |
| --- | --- | --- |
| `string` | `string` | `length`, `fixedLength` |
| `number` | `number` | `digits`, `fractionDigits`, `nonnegative` |
| `boolean` | `boolean` | |
| `date` | `date` | `parts`: `date` или `dateTime` |
| `catalog` | `CatalogRef.<Имя>` | `catalog`, `searchUrl` |
| `document` | `DocumentRef.<Имя>` | `document`, `searchUrl` |
| `enum` | `EnumRef.<Имя>` | `enumeration`, `values` с `name` и `title` |
| `valueStorage` | `ValueStorage` | значение передаётся строкой base64 |
| `uuid` | `UUID` | строка канонического UUID |
| `unsupported` | строковое имя типа платформы | поле недоступно для записи |

`searchUrl` относителен корня сервиса:
`/search?type=Справочник._ДемоПартнеры`. Имя типа в запросе кодируется как
параметр URL.

Если среди типов поля есть `unsupported`, поле целиком недоступно для записи,
даже когда рядом есть поддерживаемые типы. Описание такого типа в `types`
сохраняется.

### Какие стандартные реквизиты попадают в схему

В схему попадает реквизит, который реально есть у объекта этого вида, а не вся
выгрузка стандартных реквизитов EDT. EDT перечисляет `Parent`, `IsFolder` и
`Owner` и у тех справочников, где свойств нет.

Справочник:

| Реквизит | В схеме | Запись |
| --- | --- | --- |
| `Наименование` | Есть наименование | Да. Обязательность — из проверки заполнения |
| `Код` | Есть код и автонумерация выключена | Да. Обязательность — из проверки заполнения |
| `Код` | Есть код и автонумерация включена | Нет. Код назначает платформа |
| `ЭтоГруппа` | `hierarchical=folders` | Да, булево. Можно не передавать: новый объект — элемент |
| `Родитель` | `hierarchical` равен `folders` или `items` | Да. Пустое значение — корень |
| `Владелец` | `owners` не пуст | Да. Обязательность — из проверки заполнения |
| `Ссылка`, `ПометкаУдаления`, `Предопределенный`, `ИмяПредопределенныхДанных` | Всегда | Нет. Назначает платформа |

Документ:

| Реквизит | Запись |
| --- | --- |
| `Дата` | Да, и она обязательна по правилу сервиса |
| `Номер`, `Ссылка`, `ПометкаУдаления`, `Проведен` | Нет. Номер назначает платформа, документ записывается непроведённым |

У строки табличной части стандартные реквизиты, включая `НомерСтроки`,
описываются и не записываются. Порядок массива задаёт порядок строк.

Общий реквизит конфигурации, включённый в состав объекта, описывается с
`writable=false` и причиной, что общие реквизиты этой версией не записываются.
Табличная часть `ДополнительныеРеквизиты` описывается и не записывается:
дополнительные свойства БСП не поддерживаются. Проверку свойств БСП не
отключать и не подменять значениями. Если на стенде она не даёт создать
контрольный объект, реализацию остановить и согласовать границу. Настройки базы
не менять.

### Значения JSON

| Тип | Передача |
| --- | --- |
| Строка | Строка JSON. Длина проверяется до записи. Строка не обрезается |
| Число | Число JSON. Разрядность, точность и знак проверяются до записи. Число не округляется. Строка числом не становится |
| Булево | `true` или `false`. Строка булевым не становится |
| Дата | ISO 8601 без `Z` и без смещения. Часть «Дата» — `YYYY-MM-DD`. Дата-время — местное время базы |
| Ссылка на справочник | Строка UUID элемента |
| Ссылка на документ | Строка UUID документа |
| Перечисление | Техническое имя значения |
| Хранилище значения | Строка base64: текст элемента `{http://v8.1c.ru/8.1/data/core}ValueStorage` штатной XML-сериализации платформы, без XML-тегов |
| Уникальный идентификатор | Строка, которую даёт `XMLСтрока`. Другие формы отклоняются |
| Составной тип | Объект `{"type":"<name из схемы>","value":...}` |
| Пустое значение | `null` |

Сервис не разбирает содержимое хранилища, не меняет сжатие и не подменяет формат
на `ЗначениеВСтрокуВнутр`. При записи строка собирается обратно в
`ХранилищеЗначения` той же сериализацией. Строка, которую платформа не
принимает, отклоняется до записи прикладного объекта.

`null` означает штатное пустое значение типа, в том числе пустое хранилище и
пустой уникальный идентификатор. Для составного типа можно передать
типизированное пустое значение. Обязательность пустого значения проверяет 1С,
кроме даты документа: её отсутствие отклоняет сам сервис.

Ссылка на справочник указывает на существующий доступный элемент допустимого
справочника. Группа и помеченный на удаление элемент отклоняются. Ссылка на
документ указывает на существующий доступный документ без пометки удаления;
проведённый документ допустим. Нет объекта и нет прав — один и тот же отказ,
без сообщения, существует ли объект. Имя справочника или документа для проверки
ссылки берётся из метаданных поля, не из строки пользователя.

### Группы и владельцы

Группа создаётся тем же `POST /object`, что и элемент. При
`hierarchical=folders` в шапке передаётся `ЭтоГруппа: true`.

`Родитель`:

- `folders` — UUID группы того же справочника либо `null` для корня;
- `items` — UUID элемента того же справочника либо `null` для корня. Групп у
  такого справочника нет, поэтому `ЭтоГруппа` в схему не входит и в запросе
  отклоняется.

Родитель существует, доступен пользователю и не помечен на удаление. Чужой
справочник, элемент вместо группы при иерархии групп и группа при иерархии
элементов отклоняются тем же отказом, что и прочая неверная ссылка. Ограничение
числа уровней и состав табличных частей группы проверяет платформа при
заполнении и записи. Сервис эти ограничения не копирует.

У подчинённого справочника `Владелец` — UUID элемента одного из справочников
`owners`. Группа и помеченный на удаление владелец отклоняются. У справочника
без владельцев ключ `Владелец` неизвестен и отклоняется. И иерархический, и
подчинённый справочник передаёт оба реквизита, когда в схеме есть оба.

Решение про иерархию элементов — решение этой спецификации. Пользователь
утвердил группы и родителя-группу для иерархии групп и элементов и ту же схему
для владельца. Поведение `hierarchical=items` добавлено здесь, потому что в
базе такие справочники есть, а отдельного правила для них в сессии не было.

## Поиск объектов

Имя типа из параметра `type` сверяется с метаданными справочника или документа
до построения запроса. Текст запроса получает уже сверенное имя таблицы.
Пользовательский фрагмент в текст запроса не подставляется. Значения передаются
параметрами. Условие — `ПОДОБНО` и
`ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе`. Чтение —
`ВЫБРАТЬ РАЗРЕШЕННЫЕ`.

Строка поиска для справочника — часть наименования. У справочника без
наименования поиск получает понятный отказ, запрос не выполняется. Для
документа строка — часть номера. Отдельный индекс в расширении не заводится:
наименование справочника и номер документа уже индексируются платформой.

`q` и `limit` — те же правила, что у поиска типов. Сортировка справочника — по
наименованию, затем по ссылке. Сортировка документа — по номеру, затем по
ссылке. Запрос получает не более `limit + 1` строк.

Ответ: `items`, `hasMore`. Элемент содержит `id` и `name`. `name` справочника —
наименование, `name` документа — номер. Для `hierarchical=folders` элемент также
содержит `isFolder`. Группы и элементы входят в выдачу. Проведённые и
непроведённые документы входят в выдачу. Помеченные на удаление не входят.
Недоступные пользователю строки запрос не возвращает; это пустой результат, а
не ошибка прав.

## Создание и чтение

Порядок создания:

1. Полностью разобрать JSON, включая проверку отсутствия хвоста после значения.
2. Проверить структуру, поля и значения по схеме этого типа. Подготовить
   значения с точными типами 1С без записи прикладных объектов.
3. Создать объект, перенести шапку и строки. Не вызывать автозаполнение формы
   и обработку заполнения.
4. В транзакции очистить очередь сообщений, вызвать штатную
   `ПроверитьЗаполнение()` и собрать её сообщения. При отказе откатить
   транзакцию и вернуть ошибку.
5. Записать объект. Документ — в режиме записи без проведения, затем проверить,
   что он не проведён. Справочник — обычной записью. Запись с флагом обмена,
   обходящая штатные обработчики, запрещена.
6. Подготовить ответ чтением записанного объекта и завершить транзакцию. При
   исключении откатить её. Отказ или исключение не оставляет частично
   записанного объекта.

Чтение возвращает все поля шапки и все строки табличных частей. Поддерживаемое
значение передаётся в формате записи. Текущее значение неподдерживаемого типа
передаётся как `null`, и чтение на нём не останавливается. Поле, недоступное
для записи из-за смеси типов, при чтении всё равно отдаёт значение, если его
фактический тип поддерживается.

Не найденный и недоступный пользователю объект дают один и тот же `404`.
Помеченный на удаление объект по идентификатору читается; в `header` видна
пометка удаления. Поиск его по-прежнему не возвращает.

## Ошибки и журналирование

Форма ошибки:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Объект не прошёл проверку заполнения",
    "details": [{"path": "header.Организация", "message": "Текст проверки 1С"}]
  }
}
```

`path` — путь в запросе. Для строки таблицы путь включает индекс с нуля:
`tables.Товары[0].Номенклатура`. Для параметра URL путь — имя параметра.
Если штатное сообщение не даёт достоверно определить поле, путь равен `null`,
текст сохраняется без угадывания. Возвращаются все полученные сообщения
штатной проверки. `details` есть и у отказа с одной причиной.

| Статус | `code` | Причина |
| --- | --- | --- |
| `400` | `invalid_request` | Неверный JSON, структура, параметры, неизвестное поле, неверный тип или ссылка, неподдерживаемый вид метаданных |
| `403` | `forbidden` | Недостаточно прав на операцию |
| `404` | `not_found` | Тип справочника или документа не найден; объект не найден или недоступен |
| `415` | `unsupported_media_type` | Неподдерживаемый тип тела запроса |
| `422` | `validation_failed` | Штатная проверка заполнения отказала; объект не записан |
| `500` | `internal_error` | Неожиданное исключение 1С; при создании транзакция отменена |

Неподдерживаемый вид вроде `РегистрСведений.Имя` — `400` с ясным текстом, что
вид не поддерживается. Имя вида `Справочник` или `Документ`, которого нет в
метаданных, — `404`. Неподдерживаемые HTTP-методы отклоняет маршрутизация
платформы. Аутентификационные отказы остаются в ведении платформы и публикации.

Для сбоя клиент получает краткий текст без стека. Подробное представление
ошибки записывается в журнал регистрации, событие `СчетаМагазина`. Тело
запроса, данные авторизации и содержимое хранилища значения в журнал не пишутся.

## Проверка и приёмка

Открытие созданных объектов в 1С:Предприятии и сравнение списков до и после
отказов выполняет пользователь. Vanessa не используется. Успешный HTTP-ответ
не является проверкой формы.

Файл `tests/objects.http` содержит по одному запросу на каждый маршрут, а также
создание справочника и создание документа `_ДемоСчетНаОплатуПокупателю`. Адрес,
авторизация и UUID существующих ссылок читаются из `tests/.env`. Значения
`.env` не печатаются и не коммитятся. Ссылки в теле берутся из существующих
элементов через поиск. Новый справочник и новый документ — сами контрольные
объекты, а не подготовка посторонних данных. Новые настройки базы не создаются.

На стенде проверяются:

- каждый маршрут внешним HTTP-клиентом;
- схема действующим метаданным без ручного списка прикладных полей;
- поиск по части наименования и части номера, лимит, `hasMore`, группы в
  выдаче справочника, отсутствие помеченных на удаление;
- отказ неподдерживаемому виду метаданных, неизвестному полю и полю
  `writable=false`;
- создание группы, элемента в группе и элемента подчинённого справочника с
  владельцем;
- хранилище значения и уникальный идентификатор в чтении и записи; прочий
  неподдерживаемый тип не обрывает чтение и отклоняется на записи;
- записанные справочник и непроведённый счёт: чтение по UUID и открытие в
  клиенте 1С;
- отказ проверки заполнения не оставляет объекта; неверный JSON, тип, UUID и
  ссылка получают клиентские ошибки.

Загрузку расширения в информационную базу выполнять только по явной просьбе.
Команды загрузки не выдумываются: в репозитории нет скриптов стенда.

## Что остаётся исполнителю

Разбиение процедур внутри уже существующих серверных общих модулей
`СчетаМагазинаМетаданные` и `СчетаМагазинаДанные`, внутренние структуры обхода
метаданных, сборка параметрического запроса по правилам выше, точное извлечение
base64 из XML-сериализации хранилища и подбор существующей ссылки для
контрольного счёта. Эти решения не меняют публичный контракт, не обходят
штатную проверку и не добавляют операции.

Общие модули остаются серверными. Клиент, внешнее соединение, вызов сервера и
привилегированный режим не включать.
